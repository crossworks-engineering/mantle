# The documents engine (Gotenberg)

The second render sidecar beside the browser sidecar ([draw.md](draw.md)
section 9 for what that one does): [Gotenberg](https://gotenberg.dev)
(Apache 2.0), Chromium plus LibreOffice plus the PDF engines, in its own
container. It is the optional service **Documents** (compose service
`gotenberg`, profile `documents`, Settings > Services or
`scripts/install.sh --documents`), off by default on every shape. The plan
of record is the dev-brain page "Gotenberg beside the browser sidecar: plan
(2026-10-23)"; the decisions there: both engines run until the render jobs
are ported, Gotenberg is implemented in full first, the drawing SVG
re-render stays on the browser sidecar.

## What runs

`gotenberg/gotenberg:8.39.0` (the 8.31 line is not safe for us: before
8.38.0 every conversion shared one cookie jar, so one admin's render cookie
could authenticate a later render; the screenshot `selector` and
`deviceScaleFactor` fields arrived in 8.36 and 8.33). Measured on the dev
box (2026-10-28): 11 MiB idle, about 310 MiB after the first LibreOffice
job, 783 MiB peak during a 13-page page print, 255 to 727 MiB settled;
the compose cap is 2 GB. Image: about 700 MB to download, 2.4 GB on disk.

The container policy (docker-compose.yml, `gotenberg`):

- basic auth (`GOTENBERG_PASSWORD`, generated by `scripts/install.sh` and
  by the updater on a roll, never rotated; `/health` alone takes no
  credential, for the compose healthcheck);
- no outbound fetch at all: `downloadFrom` and webhooks are off, Chromium
  and LibreOffice deny private and public addresses, and the allow list opens exactly two things: the print origin, and on it
  only the paths a print loads (`/print/`, `/render/`, `/share-runtime/`,
  `/excalidraw-assets/`, the fonts, `/api/files/files/`, `/api/draws/`,
  `/api/presents/`, and the three icon files), so a page prints with its
  render cookie and a caller's HTML reaches no other route of the brain,
  and `file:///tmp/`, where the engine keeps the caller's own uploaded files (without it the html and
  markdown routes answer 403 once both address classes are denied);
- each conversion gets its own browser context, so a render cookie never
  outlives its job;
- two Chromium jobs at a time, ten queued; LibreOffice one at a time, ten
  queued; 60 s per request.

A hostile document can reach nothing: an outside image is refused by the
engine's proxy and the PDF renders without it; a URL route call to a public
site or to a private address answers 403.

## Wiring

`GOTENBERG_URL` (the service name in compose, the loopback port in dev) and
`GOTENBERG_PASSWORD` reach every app container through the app-env anchor,
inert until the profile is on: `serviceEnabled('documents')`
(`packages/config/src/services.ts`) reads the live profile from the
updater's `services.json`, and that one answer gates every caller. The
dashboard vitals carry a `documents` pill and Settings > Services the row,
both from `gotenbergHealth` (`packages/documents`): `GET /health` (per
module status) and `GET /version`.

Off: the documents tools are left out of an agent's tool list, MCP and the
app brokers answer that the service is off, `/api/v1/documents/*` answers
503, and page PDF export uses the browser sidecar where that runs. The
engine stores nothing, so off loses nothing.

## The package: one route table for every surface

`packages/documents` (`@mantle/documents`) owns:

- the route table (`src/routes.ts`): every Gotenberg 8.39 conversion route
  by key (the engine path without `/forms/`: `chromium/convert/html`,
  `libreoffice/convert`, `pdfengines/merge`, ...), with its input kind, the
  extra files it takes and its option schema;
- the schemas (`src/schemas.ts`): one strict zod object per route, the
  engine's own field names as the option names, grouped as the engine docs
  group them (page properties, waits, PDF/A, metadata, split, watermark,
  stamp, rotate, optimize, encryption, LibreOffice properties, screenshot
  properties). The Mantle-owned fields (`url`, `cookies`,
  `extraHttpHeaders`, `userAgent`, `downloadFrom`, the webhook fields, the
  raw file fields) are refused before the schema runs, each with why;
- the client (`src/client.ts`): fetch + FormData, basic auth, the
  `NET_TIMEOUTS.documentsJob` deadline, and one error per engine answer
  (400 a form field, 409 the job failed, 413 too large, 503 busy; off or
  unreachable is `DocumentsUnavailableError`, 503, naming the switch);
- the inputs (`src/inputs.ts`): Mantle refs only. `file_ids` are read with
  `readFileById` in the caller's scope; `node_id` (a page or a drawing)
  becomes the print URL on the print origin plus a render cookie minted
  for the caller's login (`src/render-token.ts`; the print surface answers
  403 to a cookie it refuses, so a print never shows the login page);
  inline `html` and `markdown` become `index.html` and `file.md`. Caps: 64
  MB per input, 128 MB in all, 4 MB inline, 50 files;
- the runner (`src/run.ts`): `runDocuments(call, caller, mode)` builds the
  form (with the node defaults: fail on 403 and 404, the bounded diagram
  wait, network idle, backgrounds), posts it, and lands the answer as a
  file node by the `saveExport` rules (Auto-filed / Exports for an Admin
  user, else the top of Files; `data.exportOf` the source, `data.documentsRoute`
  the route) or hands the bytes back; the two JSON routes answer JSON.

Every surface calls `runDocuments`: the HTTP API
(`server/web/lib/documents-route.ts`, the route files under
`app/api/v1/documents/`), the four agent tools, the MCP server and the app
broker (the next milestone), and the page export.

### The HTTP surface

`POST /api/v1/documents/<family>/<route>` with `{ inputs, options,
filename }`, an Admin user's session or `mtlk_` key (key area `files`), the
`documents` rate limit (30 a minute per login). The answer is the landed
file (201), the bytes with `?return=bytes`, or `{ result }` for the two
read routes. The user guide (`docs/guide/07-api/03-http-api.md`) has the
body and the inputs.

## Agents, MCP and apps

Four builtin tools (`packages/tools/src/builtins-documents.ts`), the manifest
tool group `documents` (system-wide, not Admin only: each tool runs in the
caller's scope and lands where an export lands for that caller; granted to
the persona, the pages writer and the ledger specialist; the reconcile
carries it to existing brains), and the MCP server (`packages/mcp-core`,
`registerBuiltinTools(DOCUMENT_TOOLS)`):

| Tool                | Route(s)                                                | Inputs                                                       |
| ------------------- | ------------------------------------------------------- | ------------------------------------------------------------ |
| `pdf_render`        | `chromium/convert/{url,html,markdown}` by the inputs    | `node_id`, or `html` / `markdown` (+ assets, header, footer) |
| `screenshot_render` | `chromium/screenshot/{url,html,markdown}`               | the same                                                     |
| `office_to_pdf`     | `libreoffice/convert`                                   | `file_ids`                                                   |
| `pdf_tools`         | `pdfengines/<op>` by `op` (merge, split, ..., factur_x) | `file_ids` (+ watermark, stamp, embeds)                      |

Each takes `options` (the engine's fields) and `filename`, runs as the
acting login (`currentActor`: the render cookie of a page print names it;
a call with no login actor converts files and inline text only), and
answers the landed file. While the service is off the tools are left out
of an agent's list (`toolServiceAvailable`) and MCP answers that the
service is switched off. `export_node` rasters an embedded drawing through
`chromium/screenshot/url` (2x, sized at 1x) when the service is on, so a
Word export from an agent or MCP carries real drawings; off, the drawing
degrades to `[drawing: alt]` as before.

Mini apps: an app the Admin workspace alone holds declares the tools with
`app_tools_set` and calls them with `host.tools.call` (the admin broker's
rule: a declared tool runs as the admin); `app_authoring_guide` has the
worked "Reports" example. Team apps refuse them (`TEAM_APP_TOOLS_ALLOWED`:
a conversion writes a file). This is the flagged seam of v1: landing a
report in the workspace that holds the app is a later decision.

## Pages export on the engine (stage 2, P5)

`server/web/lib/render-pdf.ts` `renderNodeToPdf` prints a page or a
drawing through `chromium/convert/url` when the service is on (the same
print surface, the render cookie the package mints for the acting admin,
the bounded diagram wait, network idle, backgrounds), and through the
browser sidecar otherwise; `lib/draw-snapshot.ts` `getDrawPngOrRender`
rasters a drawing for Word through `chromium/screenshot/url` the same way.
The print surface renders its images eager, so every picture is in before
either engine prints (task 5dda95ee). The print options
(`server/web/lib/print-options.ts`: paper, landscape, margins, a header and
a footer line, page numbers) are query parameters of
`GET /api/export/:id?format=pdf`, documented in [`pages.md`](pages.md);
both engines honour them. Nothing on the browser service is lowered: it
keeps the drawing SVG re-render (P6 is the post-back workaround, later).

## In dev

```sh
COMPOSE_PROFILES=documents pnpm infra:up
```

starts `mantle_dev_gotenberg` on `127.0.0.1:3005` with the password
`mantle`; `.env.local` sets `GOTENBERG_URL=http://127.0.0.1:3005` and
`GOTENBERG_PASSWORD=mantle` (see `.env.example`). The dev allow list opens
the native dev server on the host (`host.docker.internal:<port>`) instead
of `web:3000`.
