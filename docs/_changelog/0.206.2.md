## Fixed

### `pg_dump` resolves newest-first, so a pg18 server never meets a 17 client

v0.202.1 shipped half of the pg-client 17→18 fix — the Dockerfile now installs
`postgresql-client-18` — but the engine never caught up. On main, `resolvePgDump`
listed only `/usr/lib/postgresql/17/bin/pg_dump`, both failure messages told
operators to "install a Postgres 17 client", and `docs/backups.md` still
documented the 17 client and "the bundled Postgres 17".

The candidate list now leads with the newest pgdg path, and the messages say
"a Postgres client at least as new as the server" — the rule that actually
matters, since `pg_dump` refuses a server newer than itself while a newer client
reads older servers fine. The docs note that a `POSTGRES_IMAGE_TAG` bump has to
be matched in the Dockerfile in the same change.

One correction on top of the rescued diff: it kept the bare PATH name as the
first candidate, which leaves the case it describes open. On a host with both
clients installed, `pg_dump` on `PATH` may be the 17 binary; `canRun` probes
`--version`, which an older client passes happily before aborting on a pg18
server, so the explicit 18 path was never reached. Only ordering can distinguish
them. `/usr/lib/postgresql/18/bin/pg_dump` now goes first; `PATH` still outranks
the older explicit paths, so an operator's own choice isn't demoted below a stale
install, and `MANTLE_PG_DUMP` still wins outright.

Note this was a latent trap rather than a live outage: inside the Docker image
only the 18 client exists, so `PATH` already resolved correctly there. It bites
mixed-client hosts — the workstation among them.

### Shell tools no longer hand the child process every secret in the environment

`run_terminal` and shell-kind tools feed stdout/stderr straight back to the
model, so a single `env` or `printenv` would return the at-rest encryption key
and every API key in one call — collapsing the encryption story to "don't grant
this tool". Child env is now scrubbed by `sanitizedEnv()`: the crypto/session/db
roots by exact name (`MANTLE_MASTER_KEY`, `MANTLE_MASTER_KEY_NEXT`,
`SESSION_SECRET`, `DATABASE_URL`, `DIRECT_DATABASE_URL`) plus anything whose name
carries a secret-shaped `_`-delimited segment.

Matching whole segments rather than substrings is what keeps `MONKEY_BUSINESS`
and `KEYCLOAK_URL` while still catching `S3_SECRET_KEY` and `GITHUB_TOKEN`. An
allowlist was rejected as too breaking; `PATH`, `HOME`, `NODE_*`, `PNPM_*` and
friends all survive, so git/pnpm/builds behave exactly as before. Applied in
`dispatchShell`, so it covers every shell-kind tool rather than `run_terminal`
alone.
