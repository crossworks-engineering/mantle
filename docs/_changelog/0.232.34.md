# 0.232.34 (2026-08-22)

Files can finally go somewhere else.

## Move and copy

Since the day the files workspace existed, a file lived wherever it was
uploaded. You could rename it; you could not relocate it. Reorganising meant
download, delete, re-upload — losing the file's id, its shares, its history.

Files and folders now move and copy, with the guarantees you'd hope nobody
had to state:

- A **move** keeps the file's identity: same id, same shares, same history —
  only the location changes. Folder moves carry the whole subtree, refuse to
  move a folder into itself, and refuse name collisions with an error that
  says which name and where.
- A move also **respects the indexing switch**: a file moved into a
  name-only gallery sheds its content index automatically, and one moved out
  regains it — exactly as if the flag had been flipped. The folder move
  reports how many files it re-indexed.
- A **copy** is a genuinely new file — its own id, its own indexing under
  the destination folder's mode, no link back. Deleting the original never
  breaks the copy.
- **Folder copies stop at 200 files** and say so, with the count. Every
  copied file is re-read into the brain, which is real model spend — a big
  copy should be a decision, not a side effect. Copying into a name-only
  destination costs nothing and is the suggested route for archives.
- Disk and database move together: the bytes move first, the records follow
  in a transaction, and a failed write puts the bytes back.

Assistants get the same four verbs (`file_move`, `file_copy`, `folder_move`,
`folder_copy`), each description naming its neighbour so "move vs copy vs
rename" never has to be guessed.

The client grew the view these operations deserve: a **two-pane manager** in
the file workspace — two folders side by side, select on one side, Copy or
Move toward the other. F5 copies, F6 moves, Tab switches panes, exactly
where forty years of file managers put them.
