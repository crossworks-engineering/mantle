# 0.206.1 (2026-07-27)

**Selected rows stop bleaching themselves out everywhere else.** v0.205.7 fixed
the Pages `/` and `@` menus. The same defect lived in the shared `CommandItem`
primitive, so it was on every command surface in the app: the ⌘K search
palette, the model picker, the tag filters on Pages and Team, the table-grid
column pickers.

## Fixed

### `CommandItem` icons now derive from `accent-foreground`

The primitive already fills the selected row correctly
(`data-[selected=true]:bg-accent data-[selected=true]:text-accent-foreground`),
but its own icon rule pinned every unstyled `svg` to `text-muted-foreground`,
a token paired with `--muted`, not `--accent` (style guide §2, "pair every fill
with its OWN `-foreground`"). On a selected row the icon therefore sat on a
surface no theme makes a promise about.

The rule now flips with selection. Because it lives in the primitive, this fixes
icons on every consumer at once.

### Meta text on selected rows flips too

`CommandItem` also gained a `group/command-item` marker, so a consumer's own
secondary text can follow the row:

```
text-muted-foreground group-data-[selected=true]/command-item:text-accent-foreground
```

Applied to every place that renders muted meta text inside a command row:

- **search palette**: the nav shortcut path, a node result's summary and its
  relative timestamp, and a passage result's node-title/heading line;
- **model picker**: the model id/modality line and the custom-slug hint;
- **Pages** and **Team** tag filters, the per-tag count;
- **table grid**: the source-column type badge.

The `Superseded` badge in the search palette keeps its `text-destructive` on
purpose: the fix targets muted meta text, not deliberate semantic colour.

### Measured

Recomputed across all **86 theme/mode combinations** in
`packages/web-ui/styles/themes.css`, `muted-foreground` on `accent` vs
`accent-foreground` on `accent`:

- **29 combinations had `muted-foreground` on `accent` below 3:1.** The worst
  were effectively invisible: mocha-mousse dark **1.03:1**, sunset-horizon dark
  1.06:1, soft-pop dark 1.11:1, midnight-bloom / northern-lights / doom-64 dark
  1.18:1.
- After the change each renders at its theme's own declared accent pairing,
  e.g. mocha-mousse dark 1.03:1 → **6.67:1**, soft-pop dark 1.11:1 → 14.56:1,
  doom-64 dark 1.18:1 → 9.48:1.

## Known issue: weak `accent` / `accent-foreground` pairs

This fixes the markup, not the palettes. **11 of the 86 combinations declare an
`accent`/`accent-foreground` pair that is itself below AA (4.5:1)**, so their
rows are now consistent but still not compliant:

| Theme | Contrast |
|---|---|
| midnight-bloom dark | 2.36:1 |
| northern-lights dark | 2.36:1 |
| twitter light | 2.46:1 |
| bubblegum dark | 2.54:1 |
| starry-night light | 2.63:1 |
| catppuccin light | 2.79:1 |
| midnight-bloom light | 3.22:1 |
| nature dark | 3.47:1 |
| ocean-breeze dark | 4.02:1 |
| doom-64 light | 4.11:1 |
| violet-bloom light | 4.27:1 |

Two of these (twitter light, violet-bloom light) are cases where the theme's
`muted-foreground` happens to read *better* on `accent` than its own
`accent-foreground` does, but the row's primary text was already using
`accent-foreground`, so matching the secondary line to it is still the correct
pairing. No markup change can repair a palette whose declared pair is weak;
these need the presets themselves edited.

## Upgrading

Nothing to do, CSS classes only, no migrations, no config.
