# 0.205.0 (2026-07-26)

**API integrations become first-class.** A tool group can now BE an
integration: it carries the service's bound credential, its base URL and auth
placement, the API documentation itself (stored, indexed, readable by agents),
and a distilled usage skill that travels with every grant. Hand Toolsmith a
vendor's docs page and it stands up the whole thing, group, token binding,
stored docs, working calls, know-how, and any agent granted the group later
inherits both the capability and the judgment to use it well.

## Added

### The integration binding on tool groups

`tool_groups` gains a nullable `integration` block (migration `0137`):
`service`, `baseUrl`, `secretRef`, `authTemplate` (which header/query key the
`{{secret:…}}` ref goes under), plus links to the stored docs and the usage
skill. This is where "which token does the weather API use, and where does it
go?" now lives, decided once, at the group, instead of rediscovered inside
every authored tool.

- **Authoring-time inheritance.** `api_tool_create`/`_update` (and the
  console's *Save as agent tool*) accept a `group_slug`: the group's base URL
  prefixes a relative `url`, its auth template merges under the tool's own
  headers/query (the tool wins on conflict), and the tool joins the group in
  the same call. The **resolved** request is what gets stored, the dispatcher
  is untouched, `api_tool_get` shows exactly what will run, and every existing
  tool keeps working unchanged.
- **Secrets stay refs end to end.** The binding carries the same
  `{{secret:service/label}}` strings templates always used; the vault's
  masked-preview rules are unchanged and the group editor's credential picker
  never sees plaintext.

### Stored API documentation: `api_docs_set` / `api_docs_get`

Toolsmith used to read a vendor's docs over `web_fetch` and the knowledge
evaporated with the turn. Now the docs are written to
`files/api-docs/<group>.md` through the normal file pipeline, summarised,
embedded, searchable, with a provenance header (source URL, fetched date).
"Add the forecast endpoint" next month starts from `api_docs_get`, not from
re-fetching a page that may have moved; and any agent's `search` can find how
an API works.

### The usage skill: know-how that travels with the grant

An integration holds three kinds of knowledge: reference (the stored docs,
read on demand), selection (tool descriptions), and **usage judgment**,
which endpoint answers which question, unit conventions, how calls chain.
That third kind finally has a home: `api_skill_set` writes a short distilled
skill (`api-<group-slug>`) linked from the integration, and **granted groups'
skills now enter the agent's context**; effective skills are the agent's own
plus those of its granted, enabled groups, deduped, own-first. Grant the
weather group to a second agent and the know-how arrives with it.

`api_skill_set` is the first skill-authoring tool agents have ever had, and
it is scoped accordingly: the slug is derived, never model-supplied; a group
without an integration binding is refused; an existing skill the integration
doesn't own is refused, never overwritten. Toolsmith can distil its own
integrations' know-how, and categorically cannot touch persona or manifest
behaviour. Skills ship in every granted agent's prompt on every turn, so the
tool enforces a hard size cap and warns past ~250 words.

### Toolsmith works group-first

The prompt's workflow is now: bind the integration (picking the vault ref via
`api_key_refs`, asking rather than guessing between keys) → store the docs →
author calls with `group_slug` so auth and base inherit → test → distil the
usage skill → grant. Extending an existing integration reads the stored docs
FIRST and touches the internet only when they don't cover the endpoint.
Everything propagates through the manifest: new tools ride the `toolsmith`
group's slug spread, the prompt and the persona's `integrations` skill body
overwrite-sync on upgrade. The per-group skills themselves are runtime,
owner-space rows, never seeded, never reconciled.

### Owner-side visibility

- **Settings → Tool groups**: an Integration section on the group, service,
  base URL, credential picker (refs + masked previews), auth placement, docs
  view/replace, a link to the usage skill. Everything the agent can set, the
  owner can correct.
- **API Console** (`/dev-tools`): custom tools group under their integration
  with the bound ref badged, and the save dialog offers the integration
  picker with the same inheritance.

## Notes

- Deploys need migration `0137` (additive, nullable, no data change).
- MCP: `api_docs_set` and `api_skill_set` join the write set behind
  `MANTLE_MCP_TOOLSMITH_WRITE`; `api_docs_get` is always exposed.
- Docs: `toolsmith.md` §0 (the binding layer), `api-console.md` §2b,
  `tools-and-skills.md` (integration groups; "capability-only" clarified,
  a group may carry integration config and *reference* a skill, and granted
  groups' skills enter context, which is why usage skills stay short).
