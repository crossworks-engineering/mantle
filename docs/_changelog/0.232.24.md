# 0.232.24 (2026-08-21)

Asking a responder a question from Claude Desktop had one tool, and its name
described the opposite of what it did. There are now two tools with honest
names, and the one that runs the turn can be told not to touch anything.

## `respond_as_agent` is now `ask_responder`

The tool sends a message to one of your responder agents and gives you back
that agent's answer. The brain runs the turn: its persona, its retrieval, its
tools, its delegation edges, every guard enforced. You are the one asking.

The old name read as "respond as the agent", which sounds like you get to _be_
the responder. That is a different thing, and it now exists separately, so the
name had to go. `respond_as_agent` keeps working as a deprecated alias for one
release, so nothing pinned to it breaks on upgrade.

## `read_only`, so a probe cannot do damage

The tool's granted tools genuinely execute. That was always documented, but it
made the most obvious use of the tool unsafe: asking a live box a canary
question after a deploy, to check that chat, retrieval, tools and memory all
still work end to end. A model deciding to send an email in the middle of a
smoke test is not a hypothetical risk, it is the default behaviour of a tool
loop with an email tool in it.

Pass `read_only: true` and the turn keeps only the tools that mutate nothing
and send nothing outward.

It works by exclusion rather than permission. Every built-in tool now carries a
flag saying whether it is safe for a read-only turn, and a tool that does not
carry it is dropped. So a new write tool is locked out on the day it ships,
without anyone remembering to add it to a list, and tools you defined yourself
through the API or recipe builders are never included. Delegation is excluded
too: a child agent brings its own grants, and letting one through would undo
the whole thing. The filter runs last, after every other step that can add a
tool, so nothing puts a write tool back.

Two of the classifications were wrong when first written and the test caught
both before they shipped. `email_page` sends a page as an email despite reading
like pagination, and `run_audit` advances a run despite reading like an
inspection. That is the failure this design expects, which is why the rule is
"unmarked means excluded" rather than "unmarked means allowed".

`exclude_tools` still works and composes with it. `read_only` sets the ceiling,
`exclude_tools` narrows further.

## `ask_as_responder`, for when you want to be the persona

The genuinely different thing the old name promised. It hands you the
responder's composed system prompt, its skills, the tools it would hold and its
delegation edges, and then gets out of the way. No model call, no tool run,
nothing written. You answer as that persona, in your own loop, with your own
model, for as long as you like.

What it cannot do is make you behave. The prompt is real, but delegation edges
arrive as a list rather than a gate, the tool list is what the responder would
be granted rather than what you can reach, and confirm-gating, `/pending`
parking and the loop guards all stay on the server. The tool says so in its own
description and returns the warning in the payload, because a caller who
misreads this will believe it is sandboxed when it is not. When the rules have
to hold, `ask_responder` is the one that holds them.
